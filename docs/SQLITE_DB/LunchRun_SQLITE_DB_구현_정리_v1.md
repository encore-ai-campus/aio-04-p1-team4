# LunchRun 1~7단계 구현 정리 v1

- 작성일: 2026-11-10
- 프로젝트: `C:\TeamProject_1`
- 현재 DB: SQLite + SQLAlchemy
- 향후 DB: Supabase PostgreSQL

## 목표

사용자가 설정한 위치·반경·예산·음식 종류에 맞춰 메뉴를 선정하고, 실제 카카오 식당과 상세페이지에서 확인한 메뉴·가격·영업시간으로 식당을 추천한다. 이후 `그 식당 가격은?`, `지금 영업 중이야?` 같은 후속 질문에도 같은 대화 문맥과 DB를 사용해 답한다.

## 1단계: 챗봇 정책 확정

- Groq와 서버의 책임을 분리했다.
- Groq는 의도를 해석하고 서버가 최종 실행과 사실 검증을 담당하도록 정했다.
- 추천, 재추천, 조건 변경, 후속 질문, 범위 밖 질문의 정책을 문서화했다.
- 가격·주소·영업 여부를 AI가 임의 생성하지 않는 원칙을 정했다.

관련 문서: [초기 정책 보관본](../../docs_old/docs/chatbot_policy_v1.md)

## 2단계: 메뉴 카탈로그와 DB 후보 선정

- `menu_catalog`, `menu_alias` 테이블을 추가했다.
- 식당별 실제 `menu`와 랜덤 선정용 대표 메뉴 카탈로그를 분리했다.
- 주변 식당에서 확인된 예산 이내 메뉴를 우선하고, 부족할 때 카탈로그를 사용한다.
- `price_hint`와 실제 매장 가격을 구분했다.
- 기본 메뉴 시드를 멱등하게 등록한다.

관련 문서: `menu_catalog_design_v1.md`

## 3단계: 최근 10턴 채팅 세션

- HttpOnly UUID4 쿠키로 브라우저 세션을 구분한다.
- 최근 10턴, 현재 조건, 위치, 선택 메뉴, 최근 식당 ID와 확인 대기를 보관한다.
- 새로고침 시 `/api/chat/session`으로 상태를 복원한다.
- 쿠키에는 질문·위치·식당 정보를 넣지 않는다.
- 현재는 메모리 저장이므로 서버 재시작 시 세션이 사라진다.

관련 문서: [초기 세션 설계 보관본](../../docs_old/docs/chat_session_design_v1.md)

## 4단계: Groq v2 가드레일

- 추천·재추천·식당 검색·메뉴/식당 후속 질문·조건 변경·확인·범위 밖 의도를 구조화했다.
- 최근 10턴과 현재 메뉴, 최근 식당 ID·이름을 Groq에 전달한다.
- Pydantic으로 허용 메뉴와 최근 식당 ID만 통과시킨다.
- 잘못된 JSON은 한 번만 재요청하고 다시 실패하면 안전한 확인 응답으로 전환한다.
- 인증·한도·네트워크 오류는 형식 오류처럼 재시도하지 않는다.

관련 문서: [초기 가드레일 설계 보관본](../../docs_old/docs/groq_guardrail_design_v1.md), [정책 v2 보관본](../../docs_old/docs/chatbot_policy_v2.md)

## 5단계: 실제 DB 추천과 후속 질문

- `services.py`의 실행용 임시 메뉴 배열을 제거하고 DB 메뉴를 조회한다.
- 메뉴만 추천할 때는 카카오 검색을 실행하지 않는다.
- 식당 추천 시 `search_keyword`로 카카오 검색 후 DB에 저장한다.
- 메뉴 대표명과 별칭으로 상세페이지 메뉴를 비교한다.
- 가격·주소·메뉴·현재 영업 여부·추천 이유 질문을 DB에 연결했다.
- 누락 정보는 `가격 확인 불가`, `메뉴 확인 불가`, `현재 영업 상태 알 수 없음`으로 처리한다.

관련 문서: [DB 챗봇 설계](../db_chat_action_design_v1.md), [정책 v3 보관본](../../docs_old/docs/chatbot_policy_v3.md)

## 6단계: 스트리밍과 상세정보 재사용

- `POST /api/chat/stream` JSON Lines 스트림을 추가했다.
- 질문 해석, DB 확인, 검색, 캐시, 수집 진행률, 필터링, 완료·실패를 화면에 표시한다.
- 진행 중 스피너와 `1/3` 형태의 수집 건수를 표시한다.
- 화면 이동과 120초 초과 시 요청을 취소한다.
- 정상 상세정보는 기본 168시간, 실패 상태는 60분 동안 재사용·대기한다.
- 일부 식당 수집 실패 후에도 다음 식당을 계속 처리한다.

관련 문서: `streaming_chat_design_v1.md`, `chatbot_policy_v4.md`

## 7단계: 통합·운영 준비

- Alembic 초기 마이그레이션과 기존 DB `stamp` 절차를 추가했다.
- `/api/health`와 `/api/readiness`를 분리했다.
- 요청마다 `X-Request-ID`를 발급하고 민감정보 없는 JSON 로그를 기록한다.
- 세션별 분·일 채팅 요청 제한과 최대 요청 크기를 적용했다.
- 실제 Groq·카카오·Playwright 전체 검사를 환경변수로 분리했다.
- 운영 점검표와 PostgreSQL/Supabase 마이그레이션 준비 문서를 추가했다.

관련 문서: `integration_architecture_v1.md`, `database_migration_guide_v1.md`, `operations_checklist_v1.md`

## 현재 추천 처리 순서

1. 사용자의 위치·반경·예산·음식 종류를 검증한다.
2. Groq가 질문 의도와 대상을 구조화한다.
3. 서버가 Pydantic 가드레일을 검증한다.
4. DB에서 실제 근거 메뉴 또는 카탈로그 메뉴를 선정한다.
5. 식당 요청일 때만 카카오 장소 검색을 실행한다.
6. 식당 기본정보를 카카오 ID 기준으로 저장·갱신한다.
7. 최신 상세정보는 재사용하고 필요한 식당만 수집한다.
8. 메뉴 판매, 예산, 한국 시간 영업 여부를 판정한다.
9. 추천, 확인 필요 후보와 제외를 구분한다.
10. 결과와 식당 ID를 세션에 저장해 후속 질문에 사용한다.

## 주요 테이블

| 테이블 | 역할 |
|---|---|
| `menu_catalog` | 대표 추천 메뉴와 카카오 검색어 |
| `menu_alias` | 같은 메뉴의 다른 표기 |
| `restaurant` | 카카오 식당 기본정보 |
| `menu` | 상세페이지에서 확인한 메뉴와 가격 |
| `business_hours` | 요일별 영업 구간·휴무·익일 종료 |
| `place_detail_status` | 메뉴·영업시간 수집 상태와 성공 시각 |
