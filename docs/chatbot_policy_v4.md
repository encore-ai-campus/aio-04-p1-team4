# LunchRun 챗봇 추천 정책 v4

- 작성일: 2026-11-10
- 상태: 6단계 스트리밍·캐시 재사용 적용 버전
- 이전 버전: [정책 v3 보관본](../docs_old/docs/chatbot_policy_v3.md)

## 1. v3에서 달라진 점

- 기존 `POST /api/chat`은 유지하고 `POST /api/chat/stream`을 추가했다.
- 스트리밍 API는 JSON Lines 형식으로 현재 처리 단계를 전달한다.
- 저장된 최신 상세정보를 재사용하고 수집이 필요한 식당만 브라우저로 확인한다.
- 채팅창에는 현재 단계와 회전 스피너를 표시한다.
- 화면 이동 또는 120초 초과 시 브라우저가 요청을 취소한다.
- 같은 세션의 스트리밍 요청은 한 번에 하나만 실행한다.

## 2. 진행 이벤트

| 이벤트 | 의미 |
|---|---|
| `started` | 요청 연결 시작 |
| `interpreting` | Groq가 질문 의도와 대상을 해석 중 |
| `checking_database` | 메뉴·식당 저장정보 확인 중 |
| `searching` | 카카오 장소 검색 중 |
| `using_cache` | 최신 상세정보를 재사용 중 |
| `collecting` | 상세페이지 수집 중이며 완료/전체 건수 포함 |
| `filtering` | 메뉴·가격·영업시간 추천 조건 판정 중 |
| `completed` | 최종 검증 결과 포함 |
| `failed` | 안전한 오류 코드와 사용자 안내 포함 |

브라우저 연결이 끊어진 취소는 이미 응답을 받을 수 없으므로 별도 `cancelled` 문장을 화면에 남기지 않는다. 서버 작업 취소와 자원 정리는 연결 종료를 통해 전달한다.

## 3. 저장 데이터 재사용

- 신규 또는 `pending` 식당은 즉시 수집한다.
- 정상·정보 없음 결과는 기본 168시간 동안 재사용한다.
- 수집 실패는 기본 60분 뒤 다시 시도한다.
- 주기는 `DETAIL_SUCCESS_TTL_HOURS`, `DETAIL_FAILURE_RETRY_MINUTES`로 변경할 수 있다.
- 재수집 실패만으로 이전에 정상 저장된 메뉴와 영업시간 행을 삭제하지 않는다.
- 한 요청에서 상세수집 대상은 기존과 같이 최대 3곳이다.

## 4. 일부 실패 정책

한 식당 페이지 수집이 실패해도 다음 식당을 계속 처리한다. 최종 추천은 성공적으로 확인한 식당과 기존 최신 저장정보를 사용한다. 브라우저 자체를 열 수 없는 경우에는 대상별 실패 상태를 기록하되 이전 정상 데이터는 유지한다.

## 5. 화면 정책

- 진행 중에는 질문 입력과 빠른 질문 버튼을 비활성화한다.
- 채팅 답변 위치에 현재 처리 단계 하나만 표시한다.
- 상세수집 이벤트의 `completed/total`을 그대로 표시한다.
- `completed` 이벤트에 포함된 결과만 카드와 지도 상태에 적용한다.
- `failed` 이벤트는 스피너를 종료하고 안전한 메시지를 대화에 남긴다.
- 화면 이동이나 조건 무효화 시 `AbortController`로 이전 스트림을 취소한다.

## 6. 현재 제한

- Redis나 별도 작업 큐를 사용하지 않으므로 서버 재시작 후 진행 중 작업을 복구하지 않는다.
- 중복 방지 상태는 현재 FastAPI 프로세스 안에서만 공유된다. 여러 서버 인스턴스 운영 시 Redis 잠금이나 작업 ID가 필요하다.
- NDJSON 스트림을 중간 프록시가 버퍼링하지 않도록 응답 헤더를 설정했지만 실제 배포 프록시 설정도 확인해야 한다.
