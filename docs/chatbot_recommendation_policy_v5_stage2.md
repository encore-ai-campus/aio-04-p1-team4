# 챗봇 추천 정책 v5 — 2단계: 메뉴 선정과 식당 조회 분리

- 작업 대상: C:\temp_resolved
- 이전 기록: [1단계 추천 필터](chatbot_recommendation_policy_v5_stage1.md)
- 이 문서는 1단계 이후 변경분입니다. 가격·영업시간 누락 허용, 영업 우선·거리순 최대 3곳 정책은 계속 적용됩니다.

## 1. 변경한 동작

| 질문 | 처리 | 표시 |
|---|---|---|
| 메뉴 추천해줘 | 조건을 통과한 DB 메뉴 후보에서 하나를 무작위 선정 | 메뉴, 반경·예산·음식 종류·점심시간, 식당 조회 제안 |
| 다른 메뉴 추천해줘 | 현재 메뉴 하나만 제외하고 무작위 선정 | 새 메뉴와 조건, 식당 조회 제안 |
| 이 메뉴 파는 식당 알려줘 | 요청/세션의 현재 메뉴로 조회 | 최대 3개 식당의 이름·상품명·가격 및 누락 안내 |
| 짜장면 식당 알려줘 | 해석된 명시 메뉴를 우선하여 조회 | 다른 메뉴가 선택되어 있어도 짜장면 식당 표시 |
| 메뉴 없이 식당 조회 | 임의 메뉴를 선정하지 않고 안내 | 먼저 메뉴를 정해주세요 |

메뉴 선정 성공 후에는 `식당까지 추천해드릴까요?`를 표시합니다. 현재 메뉴가 있고 직전 답변이 조회 제안이라면 `네`, `찾아줘`도 식당 검색으로 해석하도록 기존 Groq 시스템 지침에 명시했습니다. 새 확인 버튼을 추가한 단계는 아닙니다.

재추천할 다른 후보가 없으면 `현재 메뉴를 제외하면 조건에 맞는 다른 메뉴가 없습니다. 조건을 변경해주세요.`를 표시합니다. 기존 세션 동작에 따라 실패한 재추천의 선택 메뉴는 초기화됩니다. 원래 메뉴로 자동 복귀하거나 다른 조건으로 조회하지 않습니다.

식당 조회 결과가 없으면 `현재 이 메뉴에 맞는 영업 중인 식당이 없어요. 다른 메뉴를 추천해드릴까요?`를 표시합니다. 이 문구는 현재 조건 전체를 통과한 결과가 없다는 뜻이며 예산·반경 등도 원인일 수 있습니다. 영업시간 미확인 식당은 1단계 정책에 따라 추천될 수 있고, 그때는 결과 없음 문구 대신 누락 안내를 표시합니다.

## 2. 내부 흐름과 적용 범위

1. Groq가 질문 의도와 명시한 메뉴를 해석합니다.
2. 서버가 위치·반경·음식 종류·예산·저장된 영업시간으로 후보를 판정합니다.
3. 메뉴 추천/재추천은 후보에서 메뉴만 선택하고 식당 목록 생성 함수는 호출하지 않습니다. 후보를 찾기 위한 식당·메뉴 DB 조회는 필요합니다.
4. 재추천은 현재 메뉴 ID 하나만 제외합니다. A → B → A가 가능하며 최근 10개 메뉴를 제외하지 않습니다.
5. 식당 요청일 때만 최대 3곳의 목록을 생성합니다. 명시 메뉴 > 현재 메뉴 순서로 대상을 정하며 대상이 없으면 먼저 안내합니다.
6. 서버가 만든 문장을 최상위 text와 result.message에 동일하게 넣습니다.

현재 메뉴의 대표 ID와 과거 메뉴 ID 기록은 별개입니다. recent_menu_ids는 기존처럼 보관하지만 재추천 후보를 제한하지 않습니다. 최근 10턴 대화 기억도 변경하지 않습니다.

카카오 API 신규 검색·상세페이지 수집은 이번 변경에 추가되지 않았습니다. 추천은 기존 DB 데이터만 사용합니다. price_hint 및 CSV도 새 후보 생성에 사용하지 않습니다. 조건에 표시하는 점심시간은 입력값 안내이며, 이동·식사시간을 계산해 보장하는 필터가 아닙니다.

## 3. 변경 파일

- app/services.py: 현재 메뉴만 재추천 제외, 메뉴만 추천할 때 조건·조회 제안 표시, 대상 없는 조회 방지, 식당 조회 실패 안내
- app/prompts/system_v4.txt: 메뉴/식당 의도 구분, 명시 메뉴 우선, 조회 제안에 대한 동의 해석 지침 보강. 기존 로더가 지정한 파일을 유지합니다.
- tests/test_recommendations.py: 기존 임시 DB 및 모의 Groq를 사용하는 2단계 회귀 테스트 추가
- docs/chatbot_recommendation_policy_v5_stage2.md: 이 설명과 직접 검증 절차

기존 문서·파일은 삭제하지 않았고 실제 DB나 스키마를 변경하지 않았습니다. 기존 SQLite·SQLAlchemy 경로를 사용하여 PostgreSQL에서도 동일한 조회 구조를 유지합니다.

## 4. 직접 화면에서 확인

PowerShell에서 서버를 다시 시작합니다. 이미 실행 중이면 해당 창에서 Ctrl+C로 종료한 후 실행합니다.

```powershell
cd C:\temp_resolved
.\run.ps1
```

브라우저에서 http://127.0.0.1:8000/ai 를 열고 Ctrl+F5로 새로고침합니다. 위치·반경·예산·음식 종류·점심 종료 시각을 유효하게 설정합니다. 테스트하려는 메뉴가 해당 범위의 DB 식당 상품에 연결되어 있어야 합니다.

1. **메뉴만 추천**: `메뉴 추천해줘` → 메뉴 하나, 조건 요약, `식당까지 추천해드릴까요?`가 표시되는지 확인합니다. 이번 답변에 식당 목록이 없어야 합니다.
2. **현재 메뉴 식당**: `이 메뉴 파는 식당 알려줘` → 앞서 나온 메뉴의 식당이 최대 3곳 표시되는지 확인합니다. 또는 제안 직후 `네`로 요청해 봅니다. 실제 Groq의 의도 해석이 포함되는 확인입니다.
3. **다른 메뉴**: `다른 메뉴 추천해줘` → 현재 메뉴와 다른 메뉴가 나와야 합니다. 후보가 둘이면 A → B → A가 가능합니다. 여러 후보라면 A로 즉시 돌아온다고 보장하지는 않습니다.
4. **조건 유지**: 재추천 전후에 반경·예산·음식 종류가 유지되는지 확인합니다. 이미 확인된 예산 초과 상품은 후보가 될 수 없습니다.
5. **명시 메뉴 우선**: 다른 메뉴가 선택된 상태에서 `짜장면 식당 알려줘` → 짜장면 기준으로 조회되는지 확인합니다.
6. **후보 부족**: 범위/예산을 좁혀 재추천할 다른 메뉴가 없으면 다른 후보가 없다는 안내가 나와야 합니다. 기존 메뉴가 초기화되는 것은 현재 정책입니다.
7. **식당 없음**: 선택 메뉴를 판매하는 식당이 현재 조건을 통과하지 못하면 정해진 다른 메뉴 제안 문구가 나와야 합니다. 영업시간 미확인 식당이 조건에 맞으면 누락 안내와 함께 추천될 수 있습니다.

데이터에 따라 특정 사례가 없을 수 있습니다. 실제 DB를 바꾸지 않고 아래 자동 검증을 이용할 수 있습니다. 브라우저 개발자 도구 Network의 /api/chat/stream 응답에서도 메뉴만 추천할 때 searching 이벤트가 없는지, completed.data.result.restaurants가 빈 배열인지 확인할 수 있습니다.
