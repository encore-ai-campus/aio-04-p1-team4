## 1. 사용자에게 보이는 변화

조건을 바꾸라고 말하면 별도 적용 버튼 없이 반영합니다. 변경 전후를 표시하고 바뀐 조건으로 메뉴를 다시 선정합니다.

예시: 현재 예산 10000원에서 `예산을 8천원으로 바꿔줘`

- 예산 변경 전: 10,000원 → 변경 후: 8,000원
- 바뀐 조건에 의한 메뉴는 짜장면입니다.
- 적용 조건과 식당 조회 제안

실제 메뉴는 DB 후보에 따라 달라집니다. 예산만 바꾸면 음식 종류·위치·반경 등 다른 입력은 유지합니다. 명시한 값이 이미 같으면 `이미 해당 조건이 적용되어 있습니다.`를 표시하며 메뉴·식당 목록을 새로 뽑지 않습니다.

## 2. 반경 조절

| 입력 | 서버 처리 |
|---|---|
| 반경을 줄여줘 | 현재 반경에서 50m 축소 |
| 반경을 늘려줘 | 현재 반경에서 50m 확대 |
| 반경을 100m로 바꿔줘 | 명시한 100m 적용 |
| 50m에서 더 줄여줘 | 최소 반경입니다. |
| 500m에서 더 늘려줘 | 최대 반경입니다. |

허용 범위는 기존대로 50~500m입니다. 상대 조절이 가능하면 `50 m 축소 하였습니다.` 또는 `50 m 확대 하였습니다.`를 표시합니다. 경계까지 50m 미만 남았을 때는 실제 변경 거리를 표시합니다. 예: 75m → 50m이면 `25 m 축소 하였습니다.`입니다.

Groq는 radius_adjustment를 increase/decrease로 해석합니다. 50m 산술과 경계 제한은 서버가 수행합니다. 절대 반경값과 상대 조절을 동시에 지정하는 해석은 계약 검증에서 거부합니다. 범위 밖 절대값을 임의 보정하지 않습니다.

## 3. 조건 변경과 식당 조회를 함께 요청

`한식으로 바꾸고 식당도 찾아줘`는 다음을 한 요청에서 수행합니다.

1. 변경 전후 조건 표시
2. 새 조건에서 메뉴 무작위 선정
3. `바뀐 조건에 의한 메뉴는 ○○입니다.` 표시
4. 해당 메뉴의 식당을 영업 우선·거리순으로 최대 3곳 표시

조건 변경만 요청하면 메뉴만 선정하고 `식당까지 추천해드릴까요?`를 표시합니다. 식당도 명시적으로 요청한 경우에만 목록을 생성합니다. 변경 후 후보가 없으면 `변경된 조건에 맞는 메뉴가 없습니다. 조건을 조정해주세요.`를 표시합니다. 새 조건은 유지하며 예전 메뉴·식당을 다시 끼워 넣지 않습니다.

후보 판정에는 기존 DB의 실제 상품 가격·위치·반경·음식 분류·영업시간을 사용합니다. 미확인 가격/영업시간 허용과 안내는 1단계 정책을 따릅니다. 신규 카카오 검색·상세 수집·CSV 로딩은 추가하지 않았습니다. 점심시간은 입력값 안내이며 이동·식사시간을 보장하지 않습니다.

## 4. 서버·세션·화면은 어떻게 맞추나

- Groq는 변경값과 상대 반경 방향만 해석합니다.
- 서버가 applied_patch에 실제 달라진 값만 담고 새 조건으로 메뉴·식당을 결정합니다.
- 일반/스트리밍 API 모두 실제 적용 조건을 세션에 기록합니다. 요청 당시의 예산·반경을 다시 저장하지 않습니다.
- 화면은 최종 응답을 받은 뒤 applied_patch를 즉시 공통 상태에 반영하고 새 메뉴·식당 목록을 저장합니다.
- 서버가 확정한 조건 반영 때문에 현재 요청을 잘못 취소하지 않도록 구분합니다. 반대로 요청 대기 중 사용자가 화면에서 다른 조건을 지정했다면 오래된 응답은 적용하지 않습니다.
- minutes 변경 요청만 점심 종료 시각을 새로 계산합니다. 예산·음식 종류·반경만 바꾸면 기존 종료 시각을 유지합니다.
- 실제 조건이 바뀌면 이전 표시 상품과 추천 이유 문맥을 정리합니다. 새 결과만 후속 질문 대상으로 사용합니다.
- 응답의 conditions 및 radius_m은 적용 후 값입니다. suggested_patch는 기존 응답 호환 필드로 남기되 새 서버의 즉시 변경 응답에서는 null입니다.
- 프론트의 과거 suggested_patch 응답 호환 처리는 유지하지만 현재 서버 응답에서 별도 적용 버튼을 생성하지 않습니다.

http://127.0.0.1:8000/ai 를 열고 Ctrl+F5로 새로고침합니다. 위치와 유효한 점심 종료 시각을 설정합니다. 실제 DB에 조건에 맞는 식당 상품이 있어야 메뉴가 나옵니다.

1. **예산 즉시 반영**: `예산을 8천원으로 바꿔줘` → 변경 전후와 새 메뉴/후보 없음 안내가 나오는지 확인합니다. 적용 버튼이 없어야 합니다.
2. **화면 동기화**: 홈 음식 조건 화면으로 이동하여 예산이 8000원인지 확인합니다. 다시 채팅에서 `메뉴 추천해줘`를 입력하여 예산 8000원을 쓰는지 확인합니다.
3. **상대 반경**: `반경을 줄여줘` → 50m 감소와 실제 반경이 맞는지 확인합니다. `반경을 늘려줘`로 반대로 확인합니다.
4. **최소/최대**: `반경을 50m로 바꿔줘` 후 `반경을 줄여줘` → 최소 반경 안내. `반경을 500m로 바꿔줘` 후 `반경을 늘려줘` → 최대 반경 안내.
5. **50m 미만 잔여 거리**: `반경을 75m로 바꿔줘` 후 `반경을 줄여줘` → 50m가 되고 25m 축소 안내가 나와야 합니다.
6. **결합 요청**: `중식으로 바꾸고 식당도 찾아줘` → 변경 전후·새 메뉴·최대 3곳이 한 응답에 표시되어야 합니다. 중식 DB 후보가 없다면 후보 없음이 정상입니다.
7. **후속 질문**: 결합 요청으로 나온 식당에 `첫 번째 식당 가격은?`을 물어 새 목록의 표시 상품 가격과 일치하는지 확인합니다.
8. **같은 값**: 현재 예산을 다시 지정하면 이미 적용 중이라고 안내하고 기존 메뉴/목록을 유지해야 합니다.
9. **후보 없음**: 조건을 좁혀 후보가 없어도 새 조건을 유지하고 이전 식당을 표시하지 않아야 합니다.

검증 질문을 아주 빠르게 반복하면 기존 요청 횟수 제한이 작동할 수 있습니다. 이때는 안내된 재시도 시간 후 확인합니다. 서버 재시작 시 현재 메모리 대화는 초기화됩니다.

개발자 도구 Console에서 다음으로 서버 세션을 확인할 수 있습니다.

```javascript
fetch('/api/chat/session').then(r => r.json()).then(console.log)
```

conditions.budget/cuisine, radius_m이 화면 값과 같은지 확인합니다. 표시 식당은 displayed_restaurants에서 확인합니다. 이 조회는 새로고침 시 화면 조건을 덮어쓰는 기능이 아닙니다.
