# 음식 종류와 업태 연결 v3

- 작성일: 2026-11-11
- 기존 `food_conditions_v2.md`의 맵기·채식 삭제 정책을 유지하며 음식 종류를 확장한다.
- CSV는 참고용이며 프로그램에서 읽거나 DB로 가져오지 않는다.

## 화면 선택지와 OR 매핑

| 화면 선택지 | 허용 업태 |
|---|---|
| 전체 | 업태 제한 없음 |
| 한식 | 한식 |
| 중식 | 중국식, 중식 |
| 일식/회 | 일식, 횟집 |
| 양식 | 경양식, 패밀리레스트랑, 양식 |
| 분식 | 분식 |
| 패스트푸드 | 패스트푸드 |
| 치킨 | 통닭(치킨), 호프/통닭, 치킨 |
| 도시락/구내식당 | 김밥(도시락), 도시락, 구내식당 |
| 뷔페식 | 뷔페식, 뷔페 |
| 냉면 | 냉면집 |
| 고기 | 식육(숯불구이) |
| 카페/빵 | 까페, 카페 |
| 술집 | 감성주점, 호프/통닭, 라이브카페, 정종/대포집/소주방, 술집 |
| 기타 | 기타, 외국음식전문점(인도,태국등), 퓨전요리 |

요청 표에 카카오 실제 표기인 `양식`, `카페`를 별칭으로 추가했다. `호프/통닭`은 치킨과 술집 양쪽 선택에서 허용한다. 명시하지 않은 업태를 임의로 기타에 넣지 않는다. 예를 들어 카카오 원본 `한식 > 육류,고기`는 첫 분류인 한식에 해당하며 고기로 자동 이동하지 않는다.

## 변경한 실행 로직

1. `app/food_types.py`가 API·Groq 조건 모델과 메뉴/식당 필터의 공통 분류 기준이다.
2. 홈과 조건 수정 창은 동일한 15개 선택지를 표시한다.
3. 실제 메뉴 근거를 찾을 때 식당의 업태를 먼저 비교한다. 도시락집의 비빔밥처럼 대표 메뉴 카탈로그 분류와 식당 분류가 다른 경우도 선택 업태의 실제 근거로 사용할 수 있다.
4. 주변 확인 메뉴가 없으면 기존 카탈로그 후보 규칙으로 돌아간다. 기존 DB의 `일식`은 화면에서 `일식/회`로, 별도 선택지가 제거된 `샐러드`는 `기타`로 표시한다.
5. 카카오 검색 결과에도 선택 업태 필터를 적용한다. 분류가 다르면 `cuisine_mismatch`로 제외한다.
6. 카페/빵을 실제 검색하는 경우 카카오 `CE7`을 사용하고 카페 저장도 허용한다. 일반 식당 검색은 기존 `FD6`을 사용한다.
7. `전체`는 업태 필터만 생략하며 예산·반경·현재 영업 여부는 계속 검증한다.

## 데이터와 프롬프트

- 기존 DB 업태와 카카오 상세분류는 그대로 보존한다.
- 테이블 구조와 기존 카탈로그의 저장 분류를 바꾸지 않으므로 이번 변경에는 DB 마이그레이션이 없다.
- 새 분류의 메뉴를 자동 생성하거나 CSV로 보충하지 않는다. 기존 카탈로그와 연결할 수 있는 수집 메뉴 또는 카탈로그 후보가 없으면 후보 없음 안내가 정상이다.
- 최신 시스템 프롬프트는 `system_v4.txt`이며 기존 버전은 보관한다. 예시 `examples_v3.json`, 안내 `replies_v4.json`은 유지한다.

## 직접 확인

1. 서버를 `Ctrl+C`로 종료하고 `run.ps1`로 다시 시작한다.
2. 브라우저에서 `Ctrl+F5`로 새로고침한다.
3. 홈과 조건 수정 창에 요청한 15개 선택지가 보이는지 확인한다.
4. 일식/회를 고르고 예산에 맞는 메뉴를 추첨한다. 응답의 `cuisine`이 `일식/회`인지 확인한다.
5. 중식은 저장 업태 `중식`과 `중국식`을 모두 허용한다. 치킨과 술집은 `호프/통닭`을 공통으로 허용한다.
6. 후보가 없는 분류에서 임의의 다른 음식 종류 메뉴가 나오지 않는지 확인한다.
7. 식당 찾기 시 Network 응답의 `excluded.cuisine_mismatch`로 다른 업태 제외 건수를 확인할 수 있다.

## 자동 검증

음식 분류 별칭, Pydantic 허용값, 도시락집 실제 메뉴 후보, 업태 불일치 식당 제외, 카페 그룹 검색·저장, 홈과 수정 창의 15개 항목 일치를 검증한다. 외부 카카오·Groq 호출은 기본 테스트에서 모의 처리한다.
