# LunchRun 메모리 채팅 세션 설계 v1

- 작성일: 2026-11-10
- 적용 단계: 챗봇 개편 3단계
- 적용 코드: `app/chat_sessions.py`, `app/api.py`, `app/main.py`, `frontend/app.js`

## 목적

Groq가 이후 질문에서 `그 메뉴`, `거기 가격은?` 같은 표현을 이해하려면 최근 대화와 현재 추천 상태가 필요하다. 로그인 기능과 Redis가 없는 현재 단계에서는 브라우저 쿠키와 FastAPI 프로세스 메모리를 사용한다.

쿠키에는 대화 내용을 넣지 않는다. 쿠키는 임의 UUID4 세션 ID만 보관하고, 질문·답변·조건·메뉴·식당 ID는 서버 메모리에 보관한다.

## 저장 구조

`ChatSessionState`는 다음 정보를 관리한다.

- 최근 질문·답변 10턴
- 현재 확정 조건과 위치·반경
- 현재 선정 메뉴 ID
- 최근 선정 메뉴 ID 목록
- 최근 추천 식당 ID 목록
- 최근 확인 필요 후보 ID 목록
- 추가 확인이 필요한 `pending_action`
- 마지막 동작과 상태 버전

식당의 메뉴·가격·영업시간 전체를 세션에 복사하지 않는다. 식당 ID만 저장하고 이후 후속 질문에서는 DB의 최신 값을 다시 읽는다.

## 최근 10턴

사용자 질문과 챗봇 답변 한 쌍이 한 턴이다. 11번째 턴이 저장되면 가장 오래된 한 턴을 제거한다. 현재 메뉴·조건·추천 식당 ID는 메시지 목록과 별도 필드이므로 오래된 대화가 제거돼도 유지된다.

## 쿠키

- 이름: `lunchrun_session`
- 값: 서버가 만든 UUID4
- JavaScript 접근 차단: `HttpOnly`
- 동일 사이트 요청 보호: `SameSite=Lax`
- 경로: `/`
- 기본 만료시간: 24시간
- 로컬 HTTP: `Secure=False`
- HTTPS 배포: `COOKIE_SECURE=true`

쿠키가 없거나 UUID4 형식이 아니면 새 ID를 발급한다. 서로 다른 세션 ID의 상태는 독립된 메모리 공간으로 분리한다.

## 메모리 저장소

`InMemoryChatSessionStore`는 `asyncio.Lock` 안에서 한 세션의 기록을 한 번에 갱신한다. 호출자에게는 깊은 복사본을 반환해 잠금 밖에서 원본 상태가 바뀌지 않게 한다.

세션은 마지막 성공 채팅 기록부터 기본 24시간 후 만료된다. 서버가 재시작되거나 `uvicorn --reload`가 실행되면 모든 메모리 세션이 사라진다. 이는 현재 로컬 단계의 의도된 제한이다.

## API 흐름

### POST /api/chat

1. 기존 Groq·추천 흐름을 실행한다.
2. 외부 호출과 서버 처리가 성공한 응답만 세션에 기록한다.
3. 쿠키가 없거나 잘못됐다면 새 세션 ID를 발급한다.
4. 현재 요청 조건, 메뉴와 추천 결과 ID를 함께 갱신한다.
5. 응답에 `session_version`을 포함한다.

실패한 외부 호출은 정상 대화 턴으로 기록하지 않는다.

### GET /api/chat/session

같은 브라우저가 새로고침했을 때 최근 대화와 현재 조건을 읽는다. 선정 메뉴의 표시 정보는 세션에 복사한 과거 값이 아니라 최신 `menu_catalog`에서 다시 조회한다. 응답은 `Cache-Control: no-store`로 브라우저와 프록시 캐시를 막는다.

## 화면 복원

페이지를 열면 세션 복원 API를 비동기로 호출한다. 저장 상태가 있으면 최근 질문·답변, 조건, 위치, 반경과 선정 메뉴를 화면 상태에 반영한다.

복원 요청이 진행되는 동안 사용자가 조건이나 메시지를 변경했다면 늦게 도착한 복원 응답을 적용하지 않는다.

## pending_action

현재 단계에서는 모델과 저장 기능만 준비한다. 실제 Groq 의도에 따라 값을 설정하고 다음 답변을 해석하는 연결은 4단계에서 구현한다.

지원할 기본 유형:

- `change_radius`
- `change_budget`
- `select_restaurant`
- `unsupported_input`

상세페이지 수집의 `pending`과는 별도 객체다.

## Redis 전환 지점

현재는 Redis를 사용하지 않는다. 이후 저장소 인터페이스를 Redis 구현으로 교체하면 쿠키·API·상태 모델은 유지할 수 있다. Redis 연결 전까지 서버 재시작 후 대화 복구는 지원하지 않는다.
