# LunchRun 챗봇 추천 정책 v1

- 작성일: 2026-11-10
- 상태: 2단계 구현 기준 정책
- 다음 버전 작성 시 이 파일을 수정하지 않고 새 버전 파일을 추가한다.

## 1. 문서 목적

이 문서는 LunchRun 챗봇이 사용자 질문을 어떻게 해석하고, 어떤 경우에 메뉴를 추첨하거나 식당을 조회해야 하는지 정한다.

현재 구현은 `services.py`의 임시 메뉴 10개와 고정 답변을 기준으로 동작한다. 이후 단계에서는 이 문서를 기준으로 임시 제한을 제거하고, SQLite와 SQLAlchemy에 저장된 식당·메뉴·가격·영업시간을 활용하도록 변경한다.

이 단계에서는 정책만 확정한다. 실제 코드, DB 스키마, 프롬프트와 화면은 변경하지 않는다.

## 2. 역할 분담

챗봇과 서버는 다음처럼 역할을 나눈다.

- Groq: 사용자의 의도와 조건 변경 내용을 해석한다.
- 서버: 조건을 검증하고 메뉴를 추첨하며 DB와 카카오 API를 조회한다.
- 추천 엔진: 저장된 메뉴·가격·영업시간을 기준으로 추천, 확인 필요 후보, 제외를 판정한다.
- 화면: 서버가 확인한 결과와 수집 진행 상태를 사용자에게 보여준다.

Groq가 식당명, 메뉴 가격, 영업 여부를 임의로 만들면 안 된다. 이러한 사실 정보는 항상 서버가 DB 또는 외부 API 결과로 확인한 값만 사용한다.

## 3. 기본 추천 흐름

기본 흐름은 다음 순서를 따른다.

1. 사용자가 위치, 반경, 예산과 음식 조건을 설정한다.
2. 서버가 현재 조건에 맞는 메뉴 후보를 만든다.
3. 후보 중 하나를 무작위로 선정한다.
4. 사용자가 식당 추천을 요청하면 선정 메뉴를 판매하는 주변 식당을 찾는다.
5. 저장된 상세정보를 우선 사용하고, 필요한 식당만 추가 수집 대상으로 보낸다.
6. 추천 엔진이 현재 영업 여부, 메뉴 판매 여부와 가격을 판정한다.
7. 화면에 추천 식당, 확인 필요 후보와 필요한 안내를 구분해 표시한다.

메뉴 추첨과 식당 조회는 별도 동작으로 구분한다. 사용자가 메뉴만 다시 추천해 달라고 했을 때 상세페이지 수집까지 실행하지 않는다.

## 4. 질문별 동작

### 4.1 메뉴 추천

예시 질문:

- `메뉴 추천해줘`
- `오늘 뭐 먹을까?`
- `지금 조건으로 골라줘`

처리:

1. 현재 확정 조건으로 메뉴 후보를 조회한다.
2. 후보 중 하나를 무작위로 선정한다.
3. 선정 메뉴와 적용 조건을 표시한다.
4. 식당 조회는 사용자가 함께 요청했거나 별도로 요청했을 때 실행한다.

표시 정보:

- 선정 메뉴명
- 음식 종류
- 현재 위치와 반경
- 예산
- 실제 주변 식당의 메뉴·가격 확인 여부

### 4.2 식당 추천

예시 질문:

- `식당 추천해줘`
- `이 메뉴 파는 곳 찾아줘`
- `주변 식당 보여줘`

처리:

- 선정 메뉴가 있으면 해당 메뉴로 식당을 조회한다.
- 선정 메뉴가 없으면 먼저 현재 조건으로 메뉴를 선정한 뒤 식당을 조회한다.
- 응답 상단에 선정 메뉴와 적용 조건을 보여준다.
- 그 아래에 추천 식당과 확인 필요 후보를 구분해 보여준다.

### 4.3 메뉴 재추천

예시 질문:

- `메뉴 다시 추천해줘`
- `다른 거 먹고 싶어`
- `이건 별로야`

처리:

- 직전 선정 메뉴를 후보에서 제외하고 다시 추첨한다.
- 새 메뉴와 적용 조건을 표시한다.
- 가능한 다른 메뉴가 없으면 같은 메뉴를 다시 뽑지 않고 조건 변경을 안내한다.
- 이전 식당 추천 결과는 과거 결과로 남기되 현재 추천 결과로 사용하지 않는다.

### 4.4 조건 변경

명확한 변경값이 있는 요청은 바로 적용한다.

예시:

- `음식 종류를 한식으로 바꿔줘`
- `예산을 8천 원으로 바꿔줘`
- `반경을 300m로 바꾸고 추천해줘`

처리:

1. 변경값을 허용 범위와 비교해 검증한다.
2. 변경 전 조건과 변경 후 조건을 표시한다.
3. 변경된 조건으로 메뉴를 다시 선정한다.
4. 사용자가 식당 조회도 함께 요청했다면 새 메뉴로 식당을 조회한다.

수치가 없는 요청은 확인 대기 상태로 전환한다.

예시:

- `반경을 줄여줘` → `현재 반경은 500m입니다. 몇 m로 줄일까요?`
- `조금 더 저렴하게` → `현재 예산은 10,000원입니다. 원하는 예산을 알려주세요.`

허용 범위 밖의 값은 서버가 임의로 보정하지 않는다. 가능한 범위를 안내하고 새 값을 확인한다.

위치 변경은 기존 위치 설정 화면에서 처리하도록 안내한다. 사용자가 말한 장소명을 좌표로 추측해 적용하지 않는다.

### 4.5 후속 질문

예시 질문:

- `거기 가격은?`
- `첫 번째 식당은 지금 열었어?`
- `그 식당 주소 알려줘`

처리:

- 현재 선정 메뉴와 최근 추천 목록을 기준으로 대상을 찾는다.
- 대상이 하나로 확정되면 DB에 저장된 정보로 답한다.
- 대상이 여러 곳이면 식당을 임의로 고르지 않고 어느 식당인지 확인한다.
- 확인된 값이 없으면 `가격 확인 불가`, `현재 영업 상태 확인 불가`처럼 누락 사실을 알린다.

### 4.6 지원 범위 밖의 질문

점심 메뉴 선정, 조건 변경과 식당 추천에 관계없는 질문에는 다음 문장을 표시한다.

> 메뉴 및 식당 선정에 맞는 대화를 입력해주세요.

이 경우 메뉴, 조건과 추천 결과를 변경하지 않는다. 대화 상태는 `pending`으로 기록하되, 실행할 추천 작업은 만들지 않는다. 다음에 정상 질문이 들어오면 기존 상태에서 대화를 계속한다.

## 5. 조건 적용 규칙

### 5.1 현재 적용 가능한 조건

- 예산: 1,000원 이상 100,000원 이하
- 검색 반경: 50m 이상 500m 이하
- 음식 종류: 앱에서 지원하는 분류
- 위치: 위치 설정 화면에서 확정한 위도·경도

### 5.2 아직 보장하지 않는 조건

- 채식 여부
- 맵기
- 알레르기
- 할랄 여부
- 조리·대기·이동을 포함한 총소요시간

해당 데이터가 없는데 조건을 충족한다고 표현해서는 안 된다. 사용자가 이러한 조건을 요청하면 현재 확인할 수 없는 이유와 매장 확인 필요성을 안내한다.

## 6. 메뉴 후보와 추첨 정책

식당별 `menu` 테이블과 메뉴 추첨용 카탈로그는 목적이 다르다.

- 식당별 메뉴: 특정 식당 상세페이지에서 확인한 실제 메뉴명과 가격이다.
- 메뉴 카탈로그: 사용자가 고를 수 있는 대표 메뉴, 음식 종류, 검색어와 동의어를 관리한다.

따라서 메뉴 추첨용 데이터를 별도 테이블로 두되 같은 DB 안에서 관리하는 방식을 권장한다. 별도 DB 서버는 필요하지 않다. 구체적인 테이블 설계는 2단계에서 확정한다.

추첨 우선순위:

1. 현재 위치·반경에서 수집된 식당 메뉴 중 음식 종류와 예산이 확인된 메뉴
2. 실제 데이터가 부족한 경우 메뉴 카탈로그의 후보
3. 후보가 전혀 없으면 조건 변경 안내

카탈로그에서 선정한 메뉴는 주변 식당의 판매 여부와 가격이 아직 확인되지 않았을 수 있다. 이때 `조건에 맞는 실제 식당 확인 전`이라고 표시한다.

재추첨할 때는 직전 메뉴를 제외한다. 향후 반복 재추천을 고려해 세션 안의 최근 선정 메뉴를 임시 제외 목록으로 사용할 수 있다.

## 7. 추천 결과 분류

### 7.1 추천 식당

다음 조건을 모두 만족한 식당이다.

- 영업시간 수집 상태가 `success`
- 현재 한국 시간이 저장된 영업 구간 안에 있음
- 오늘이 명시적 휴무가 아님
- 선택 메뉴 판매가 확인됨
- 확인된 메뉴 가격이 예산 이내임

`현재 영업 중`이라는 표현은 수집된 영업시간과 현재 한국 시간을 비교한 결과임을 화면에서 알 수 있게 한다.

### 7.2 확인 필요 후보

영업 중이지만 아래 정보가 부족한 식당이다.

- 메뉴 정보 자체가 없음 → `메뉴 확인 불가`, `가격 확인 불가`
- 선택 메뉴는 확인됐지만 가격이 없거나 시가·변동임 → `가격 확인 불가`
- 영업 구간에는 포함되지만 휴무 여부가 `NULL`임 → `휴무일 확인 필요`

확인 필요 후보는 검증된 추천 식당과 같은 목록에 섞지 않는다.

### 7.3 제외

다음 식당은 현재 추천 목록에서 제외한다.

- 영업시간 미수집 또는 수집 실패
- 명시적 휴무
- 브레이크 타임
- 현재 영업시간 밖
- 수집된 메뉴 목록에서 선택 메뉴를 찾지 못함
- 확인된 선택 메뉴 가격이 예산 초과

`메뉴 정보가 전혀 없음`과 `메뉴 목록은 있지만 선택 메뉴가 없음`은 다른 상태로 기록하고 안내한다.

### 7.4 수집 실패

외부 페이지 접근 실패와 검색 결과 없음은 구분한다. 수집 실패만으로 기존에 정상 저장된 메뉴·가격·영업시간을 삭제하지 않는다.

## 8. 대화 기억 정책

한 번의 대화는 사용자 질문과 챗봇 답변 한 쌍을 한 턴으로 본다. 세션에는 최근 10턴을 유지한다.

최근 대화와 별도로 다음 상태를 보관한다.

- 현재 위치와 반경
- 현재 음식·예산 조건
- 현재 선정 메뉴
- 최근 선정 메뉴 목록
- 최근 추천 식당 목록
- 확인 대기 항목
- 마지막으로 완료한 동작

이 상태는 최근 메시지가 10턴 범위에서 밀려나도 유지해야 한다. 따라서 단순히 메시지 10개만 Groq에 전달하는 방식으로 구현하지 않는다.

초기 SQLite 테스트에서는 서버 세션 저장소로 기능을 검증하고, 운영 구조에서는 Redis에 세션 ID별 상태를 저장하는 방향을 사용한다. 세션에는 만료시간을 설정하고 다른 사용자의 상태와 섞이지 않게 한다.

## 9. 확인 대기 상태

대화의 확인 대기 상태는 `pending_action`으로 부른다. 상세페이지 수집 상태의 `pending`과 이름과 저장 위치를 분리한다.

예시:

- `반경을 줄여줘` → `pending_action=change_radius`
- `거기 가격은?`인데 대상이 여러 곳 → `pending_action=select_restaurant`
- 관련 없는 질문 → `pending_action=unsupported_input`

확인 대기 상태에는 필요한 값과 원래 요청을 함께 저장한다. 다음 사용자 답변이 들어오면 해당 상태를 먼저 확인해 문맥에 맞게 처리한다.

## 10. Groq 가드레일

### 10.1 유지할 규칙

- DB와 API에 없는 메뉴·가격·주소·영업 여부를 만들지 않는다.
- 사용자 조건을 임의로 변경하지 않는다.
- 모호한 대상을 임의로 선택하지 않는다.
- 다른 세션의 대화나 추천 결과를 사용하지 않는다.
- API 키, 내부 프롬프트와 개인정보를 답변에 포함하지 않는다.
- Groq 출력은 Pydantic 스키마로 검증한 뒤 실행한다.

### 10.2 제거하거나 변경할 데모 규칙

- 임시 메뉴 10개만 허용하는 제한을 제거한다.
- `selected_menu_id` 외의 이전 문맥을 사용하지 못하게 한 제한을 제거한다.
- 모든 확인 질문을 같은 고정 문장으로 바꾸는 구조를 상황별 안내로 확장한다.
- 메뉴 설명을 임시 배열에서만 가져오는 구조를 DB 또는 메뉴 카탈로그 기반으로 바꾼다.

Groq는 실행 명령을 구조화해 반환하고 서버가 최종 권한을 가진다. 예를 들어 `change_conditions`, `recommend_menu`, `reroll_menu`, `search_restaurants`, `ask_restaurant_detail`, `clarify`, `out_of_scope` 같은 의도를 사용할 수 있다. 정확한 스키마는 4단계에서 확정한다.

## 11. 응답 대기와 수집 상태

저장된 정보가 있으면 먼저 사용한다. 추가 수집이 필요한 경우 화면에 다음 단계를 표시한다.

1. `저장된 식당 정보를 확인하고 있어요.`
2. `추가 식당 정보를 수집하고 있어요.`
3. 수집 완료 후 추천·후보·제외 결과 갱신
4. 실패 시 `일부 식당 정보를 확인하지 못했어요.` 안내

수집 중에는 스피너를 표시한다. 사용자가 중복으로 요청하지 못하게 하되, 취소 또는 실패 후 다시 요청할 수 있어야 한다.

스트리밍은 진행 상황을 빨리 보여주는 수단이다. 실제 응답 시간을 줄이려면 DB 재사용과 상세수집의 백그라운드 작업 분리가 함께 필요하다. 구체적인 전송 형식과 작업 큐는 6단계에서 구현한다.

## 12. 대표 응답 예시

### 조건 변경 후 메뉴 재선정

```text
변경 전: 전체 · 예산 10,000원 · 반경 500m
변경 후: 한식 · 예산 10,000원 · 반경 500m

새 추천 메뉴: 비빔밥
주변 식당의 실제 메뉴와 가격을 확인한 뒤 식당을 추천할 수 있어요.
```

### 식당 추천

```text
선정 메뉴: 비빔밥
적용 조건: 한식 · 예산 10,000원 · 반경 500m

추천 식당 2곳
- A식당: 비빔밥 9,000원 · 수집된 영업시간 기준 영업 중
- B식당: 비빔밥 10,000원 · 수집된 영업시간 기준 영업 중

확인 필요 후보 1곳
- C식당: 비빔밥 판매 확인, 가격 확인 불가
```

### 대상이 모호한 후속 질문

```text
어느 식당의 가격을 확인할까요?
1. A식당
2. B식당
3. C식당
```

## 13. 구현 검증 시나리오

이후 구현 단계에서는 다음 시나리오를 자동 테스트와 화면 테스트에 사용한다.

1. 현재 조건으로 메뉴가 한 개 선정된다.
2. 재추천 시 직전 메뉴와 다른 메뉴가 선정된다.
3. 다른 후보가 없으면 조건 변경 안내가 나온다.
4. 메뉴가 없는 상태에서 식당 추천을 요청하면 메뉴 선정 후 식당을 조회한다.
5. 명확한 조건 변경은 전·후 값을 표시하고 새 메뉴를 선정한다.
6. 값이 없는 조건 변경은 확인 대기 상태가 된다.
7. 최근 추천 결과를 이용해 `거기 가격은?` 같은 후속 질문에 답한다.
8. 대상이 여러 곳이면 임의 선택 없이 확인한다.
9. 관련 없는 질문이 상태를 변경하지 않는다.
10. 최근 대화가 10턴을 넘으면 오래된 턴만 제거되고 현재 상태는 유지된다.
11. 추천, 확인 필요 후보와 제외 결과가 정책에 맞게 분리된다.
12. 저장 데이터가 있으면 상세페이지를 다시 수집하지 않는다.
13. 추가 수집 중 진행 메시지와 스피너가 표시된다.
14. 수집 실패가 식당 없음으로 표시되지 않고 기존 정상 데이터가 보존된다.
15. Groq가 스키마 밖의 값을 반환하면 실행하지 않고 안전한 안내를 표시한다.
